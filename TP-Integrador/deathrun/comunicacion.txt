1. SEÑALES DEL SISTEMA (GODOT SIGNALS) Y PATRÓN OBSERVER
¿Qué son las Señales en Godot?
Las señales (signals) son el mecanismo de comunicación asíncrona local de Godot basado en el 
patrón Observer. Son eventos que un objeto puede emitir cuando algo importante sucede, 
y otros objetos pueden "escuchar" esas señales para reaccionar.

Características clave:
Desacoplamiento: El emisor no necesita referencias directas a los receptores
Comunicación 1-a-N: Una señal puede tener múltiples observadores
Asíncrono: Los observadores reaccionan cuando ocurre el evento, no antes
Type-safe: Godot verifica tipos en tiempo de compilación

------------------------------------------------------
Patrón Observer en tu juego:
# En spike_trap.gd (EMISOR)
signal trap_activated(trap_id)
signal trap_deactivated(trap_id)
signal player_hit(trap_id)

func activate():
    # ... lógica de activación ...
    trap_activated.emit(trap_id)  # 🔔 EMITE la señal

# En trap_manager.gd (OBSERVADOR)
func register_trap(trap_node):
    # Conecta la señal del emisor al método del observador
    trap_node.trap_activated.connect(_on_trap_activated)  # 📡 SUSCRIBE
    trap_node.trap_deactivated.connect(_on_trap_deactivated)
    trap_node.player_hit.connect(_on_player_hit)

# Callbacks que responden a las señales
func _on_trap_activated(trap_id):
    stats.active_traps += 1
    stats.total_activations += 1
    print("Trampa %d ACTIVADA" % trap_id)

PARTE 2: RPC (REMOTE PROCEDURE CALL)


¿Qué es RPC?
RPC = Remote Procedure Call (Llamada a Procedimiento Remoto)
Es un mecanismo que permite a un peer (computadora) ejecutar una función en otro peer
a través de la red. Es como hacer una llamada de función normal, pero el código se 
ejecuta en otra máquina. 

┌─────────────────────────────────────────────────┐
│              SERVIDOR (HOST)                    │
│          Peer ID: 1 (siempre)                   │
│  ┌───────────────────────────────────────────┐  │
│  │ - Procesa TODA la lógica del juego        │  │
│  │ - Movimiento del jugador                  │  │
│  │ - Física y colisiones                     │  │
│  │ - Estados de las trampas                  │  │
│  │ - Decide quién muere, dónde está cada uno │  │
│  └───────────────────────────────────────────┘  │
│                    │                            │
│                    │ RPC (sincronización)       │
│                    ▼                            │
└────────────────────┬────────────────────────────┘
                     │
                     │ Internet/LAN
                     │
┌────────────────────▼────────────────────────────┐
│            CLIENTE (TRAP MASTER)                │
│           Peer ID: 2, 3, ... (dinámico)        │
│  ┌───────────────────────────────────────────┐  │
│  │ - NO procesa lógica del juego             │  │
│  │ - Solo VISUALIZA lo que el servidor dice │  │
│  │ - Envía INPUTS al servidor (RPC)         │  │
│  │ - Recibe ESTADOS del servidor (RPC)      │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘

Principio fundamental: El servidor tiene la AUTORIDAD (Server-Authoritative Architecture)
Solo el servidor decide qué es verdad
Los clientes son "tontos": solo muestran y envían inputs
Previene trampas (un cliente no puede hacerse invencible modificando su código)

RPC en Acción: Sincronización del Movimiento del Jugado
# En player.gd, dentro de _physics_process():

# ===== PASO 1: Procesar movimiento (SOLO EN SERVIDOR) =====
func _physics_process(delta: float) -> void:
    if not is_alive:
        return
    
    # ... lógica de gravedad, salto, movimiento ...
    move_and_slide()  # ← Esto modifica 'global_position' y 'velocity'
    
    # ===== PASO 2: Sincronizar a clientes =====
    if multiplayer.is_server() and NetworkManager.is_multiplayer_active():
        rpc("sync_position", global_position, velocity)
        # ↑ Envía un mensaje de red a TODOS los clientes

rpc("sync_position", global_position, velocity)
rpc(...): Función de Godot que envía un mensaje de red
"sync_position": Nombre del método a ejecutar remotamente
global_position, velocity: Parámetros que se envían serializados por red

Receptor del RPC (en todos los clientes):
@rpc("authority", "unreliable")
func sync_position(pos: Vector2, vel: Vector2) -> void:
    # Este código se ejecuta en el CLIENTE, no en el servidor
    if not multiplayer.is_server():
        global_position = pos  # Actualiza la posición visual del jugador
        velocity = vel

@rpc("authority", "unreliable")
     └─────┬─────┘  └────┬─────┘
           │             │
           │             └─> Modo de transferencia
           └─> Quién puede llamarlo

"authority": Solo el peer con autoridad puede llamar este RPC (en este caso, el servidor)
    Si un cliente intenta llamar rpc("sync_position", ...), se ignora
"unreliable": UDP, sin garantía de entrega
    Más rápido, pero puede perder paquetes
    OK para sincronización de posición porque se envía 60 veces por segundo
    Si se pierde 1 frame, el siguiente lo corrige

Observaciones clave:
    El cliente nunca procesa input del jugador, solo renderiza
    Si hay lag de red (50ms), el cliente verá al jugador con 50ms de retraso
    El parámetro "unreliable" permite perder paquetes sin bloquear la red

# En trap_master.gd (CLIENTE)
func activate_selected_trap():
    var trap_id = available_traps[selected_trap_index]
    
    if NetworkManager.is_multiplayer_active():
        var server_trap_manager = get_node_or_null("/root/Level01/TrapManager")
        
        if server_trap_manager:
            # RPC dirigido SOLO al servidor (peer ID 1)
            server_trap_manager.rpc_id(1, "remote_activate_trap", trap_id)
            #                   ↑
            #                   └─ Solo envía al peer ID 1 (servidor)

# En trap_manager.gd (SERVIDOR)
@rpc("any_peer", "call_remote", "reliable")
#    └──┬────┘   └────┬──────┘  └───┬────┘
#       │            │              │
#       │            │              └─> TCP, garantiza entrega
#       │            └─> No ejecuta en el peer que lo llama
#       └─> Cualquier peer puede llamar (pero se valida internamente)

func remote_activate_trap(trap_id: int):
    # VALIDACIÓN DE SEGURIDAD
    if not multiplayer.is_server():
        return  # Si un cliente malicioso intenta ejecutar esto localmente, se ignora
    
    activate_trap(trap_id)


# En spike_trap.gd (sincronización bidireccional)
func set_state(new_state: TrapState):
    current_state = new_state
    # ... cambiar colisiones, timers, etc ...
    
    # SINCRONIZAR A TODOS LOS CLIENTES
    if multiplayer.is_server() and NetworkManager.is_multiplayer_active():
        rpc("sync_trap_state", new_state)
        #   ↑ Sin rpc_id(), envía a TODOS los peers

@rpc("authority", "call_remote", "reliable")
#    └──┬────┘   └────┬──────┘  └───┬────┘
#       │            │              └─> TCP, no puede fallar
#       │            └─> No ejecuta en servidor
#       └─> Solo el servidor puede llamarlo

func sync_trap_state(state: int):
    if not multiplayer.is_server():  # Solo clientes ejecutan esto
        current_state = state as TrapState
        update_visual()
        match current_state:
            TrapState.ACTIVATING, TrapState.ACTIVE:
                animate_up()
            TrapState.INACTIVE, TrapState.COOLDOWN:
                animate_down()

PARTE 3: RELACIÓN ENTRE SEÑALES Y RPC
Ahora llegamos a la parte más interesante: ¿cómo interactúan las señales locales con los RPCs de red?
Patrón Híbrido: Señales Locales + RPC para Sincronización
Tu juego usa un patrón muy elegante:

[SERVIDOR]                                    [CLIENTE]
═══════════                                   ═══════════

1. Evento local ocurre
   │
   ├─> trap.set_state(ACTIVE)
   │   │
   │   ├─> 🔔 trap_activated.emit(trap_id)   (señal LOCAL)
   │   │   └─> TrapManager._on_trap_activated()
   │   │       └─> stats.active_traps += 1
   │   │
   │   └─> rpc("sync_trap_state", ACTIVE)    (RPC de RED)
   │       │
   │       └──────────────────────────────────> 2. Cliente recibe RPC
                                                   │
                                                   └─> sync_trap_state(ACTIVE)
                                                       │
                                                       └─> current_state = ACTIVE
                                                           update_visual()
                                                           
                                                       (¡NO emite señal local!)


Observación crítica: En el cliente, cuando se recibe sync_trap_state(), NO se emiten señales 
(trap_activated.emit() no se llama). ¿Por qué?

# En spike_trap.gd
func set_state(new_state: TrapState):
    current_state = new_state
    # ...
    
    # Solo el servidor sincroniza Y emite señales
    if multiplayer.is_server() and NetworkManager.is_multiplayer_active():
        rpc("sync_trap_state", new_state)

@rpc("authority", "call_remote", "reliable")
func sync_trap_state(state: int):
    # Los clientes SOLO actualizan visual, no la lógica
    if not multiplayer.is_server():
        current_state = state as TrapState
        update_visual()
        # ← NO llama a trap_activated.emit()

Razón: Las señales son para lógica local. En el cliente, no hay TrapManager procesando lógica 
(no hay stats a actualizar), solo está renderizando. Si emitieras la señal en el cliente, 
intentaría procesar lógica que no debe procesar.

🎮 PARTE 4: IMPACTO DEL GAMEMANAGER
El GameManager es un Autoload (singleton global) que NO participa directamente en la comunicación multiplayer, 
pero es crucial para la coordinación del estado del juego.


Rol del GameManager en el Contexto Multiplayer
# game_manager.gd
extends Node  # ← Es un Autoload, existe en AMBOS peers

var game_mode: String = "single"  # ← Variable REPLICADA manualmente
var total_deaths: int = 0
var run_deaths: int = 0

Característica clave: Cada peer tiene su propia instancia del GameManager. No se sincronizan automáticamente.

[SERVIDOR]                      [CLIENTE]
GameManager                     GameManager
├─ game_mode = "multiplayer"    ├─ game_mode = "multiplayer"  ← Mismo valor
├─ total_deaths = 5             ├─ total_deaths = 0           ← ¡Diferente!
└─ run_deaths = 2               └─ run_deaths = 0             ← ¡Diferente!

¿Por qué están desincronizados?
Mira cómo se usa:

# En player.gd (línea 114)
func die():
    # ...
    await tween.finished
    GameManager.register_death()  # ← Llamada LOCAL, no RPC
    respawn()

# En game_manager.gd
func register_death() -> void:
    total_deaths += 1  # ← Solo incrementa en el peer que lo llama
    if level_running:
        run_deaths += 1


Análisis:
Solo el servidor procesa player._physics_process() → solo el servidor llama die()
    Por lo tanto, solo el servidor incrementa total_deaths
El cliente nunca llama die() (el jugador está deshabilitado en el cliente)
Resultado: El contador de muertes solo existe en el servidor

¿Es esto un problema? En tu caso, no, porque:
    Solo el host (servidor) ve la pantalla de victoria con las stats
    El Trap Master (cliente) no necesita ver stats detalladas


Coordinación del Modo de Juego vía GameManager
El GameManager sí sincroniza el modo de juego, pero manualmente:

# En lobby_menu.gd (se ejecuta en AMBOS peers)
func start_game():
    GameManager.game_mode = "multiplayer_online"  # ← Ambos establecen lo mismo
    get_tree().change_scene_to_file("res://scenes/levels/Level_01.tscn")

# En level_01.gd (se ejecuta en AMBOS peers)
func setup_multiplayer():
    if multiplayer.is_server():  # ← Cada peer decide su rol
        print("Configurado como HOST (Runner)")
        # ... lógica del runner ...
    else:
        print("Configurado como CLIENT (Trap Master)")
        # ... lógica del trap master ...


Flujo de sincronización implícita:

T=0: LobbyMenu en HOST
     └─> GameManager.game_mode = "multiplayer_online"
     └─> change_scene("Level_01.tscn")

T=0: LobbyMenu en CLIENT (al mismo tiempo, diferente máquina)
     └─> GameManager.game_mode = "multiplayer_online"  ← Mismo valor!
     └─> change_scene("Level_01.tscn")

T=1: Level_01 en HOST
     └─> multiplayer.is_server() == true
         └─> Configura como Runner

T=1: Level_01 en CLIENT
     └─> multiplayer.is_server() == false
         └─> Configura como Trap Master

No hay RPC porque no es necesario: ambos peers ejecutan el mismo código y llegan a la misma 
conclusión por caminos deterministas.

🎓 RESUMEN CONCEPTUAL
Señales (Patrón Observer)
    Propósito: Comunicación local dentro del mismo peer
    Ventaja: Desacoplamiento (emisor no conoce receptores)
    Ejemplo: trap_activated.emit() → TrapManager._on_trap_activated()
    Alcance: Solo dentro de la misma instancia del juego

RPC (Remote Procedure Call)
    Propósito: Comunicación de red entre peers 
    Ventaja: Sincronización de estado entre servidor y clientes
    Ejemplo: rpc("sync_position", pos, vel) → Cliente actualiza posición visual
    Alcance: A través de la red (Internet/LAN)

Evento físico → Servidor procesa → 🔔 Señal local + 📡 RPC de red
                                    │              │
                                    ▼              ▼
                              Stats locales    Clientes sincronizan

GameManager
Rol: Singleton global con estado NO sincronizado automáticamente
Uso: Coordina modo de juego, stats (solo en servidor en tu caso)
Limitación: Cada peer tiene su propia instancia independiente

ESTADO COMPARTIDO VS ESTADO LOCAL
==================================

Variable                      | Dónde vive                    | Se sincroniza? | Método
------------------------------|-------------------------------|----------------|--------------------------------------------------
player.global_position        | Servidor (authoritative)      | SÍ             | RPC sync_position() cada frame
player.velocity               | Servidor                      | SÍ             | RPC sync_position() cada frame
trap.current_state            | Servidor                      | SÍ             | RPC sync_trap_state() cuando cambia
GameManager.total_deaths      | Cada peer independiente       | NO             | Solo el servidor lo incrementa
GameManager.game_mode         | Cada peer independiente       | "SÍ" (manual)  | Ambos lo establecen con el mismo valor antes de entrar al nivel
TrapManager.stats             | Solo en servidor              | NO             | Solo existe en el servidor; el cliente no tiene TrapManager
TrapMaster.selected_trap_index| Solo en cliente               | NO             | UI local del Trap Master


EXPLICACIÓN DETALLADA:
======================

1. player.global_position y player.velocity
   - El servidor calcula la posición física real del jugador
   - Se envía 60 veces por segundo a los clientes vía RPC
   - Modo: "unreliable" (UDP) porque se envía constantemente
   - Los clientes solo muestran la posición, no la calculan

2. trap.current_state
   - El servidor es dueño del estado de cada trampa
   - Cuando cambia (INACTIVE → ACTIVATING → ACTIVE → COOLDOWN)
   - Se sincroniza vía RPC a todos los clientes
   - Modo: "reliable" (TCP) porque es información crítica

3. GameManager.total_deaths
   - Cada peer tiene su propia copia del GameManager
   - Solo el servidor llama player.die() → GameManager.register_death()
   - El cliente nunca incrementa el contador
   - Resultado: servidor tiene el conteo real, cliente tiene 0

4. GameManager.game_mode
   - No hay RPC explícito
   - Ambos peers ejecutan el mismo código en LobbyMenu:
     * GameManager.game_mode = "multiplayer_online"
     * get_tree().change_scene_to_file("Level_01.tscn")
   - Se "sincronizan" porque ambos establecen el mismo valor

5. TrapManager.stats
   - Solo existe en el servidor
   - El cliente destruye su TrapMaster en level_01.gd
   - Por lo tanto, no hay stats en el cliente
   - No se sincroniza porque el cliente no las necesita

6. TrapMaster.selected_trap_index
   - Variable local de la UI del Trap Master
   - Solo existe en el cliente
   - El servidor nunca necesita saber qué trampa está seleccionando el Trap Master
   - Solo cuando se ACTIVA una trampa, se envía el trap_id al servidor vía RPC
